## 零、竞争格局：我们面对的是谁？

在列出100个方向之前，必须回答一个根本问题：**一个玩家为什么要放弃现有启动器选择 Bonjour？**

### 0.1 主要竞品画像

| 竞品                       | 核心优势                                                          | 关键弱点                                                                 |
| ------------------------ | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| **PCL2**                 | 国内用户量最大；社区资源整合极深（CurseForge/Modrinth 直搜+中文适配）；整合包安装体验成熟；免费无广告 | WPF/.NET 技术栈老旧，重构困难；仅支持 Windows；UI 风格偏传统，缺乏现代设计感；启动慢（.NET 冷启动 5-8 秒） |
| **HMCL**                 | 开源社区驱动；跨平台（Java）；功能最全面（版本继承解析、模组依赖管理、光影管理等均自研）；插件扩展机制         | JavaFX 性能瓶颈，界面卡顿；启动速度受 JVM 影响；UI/UX 设计感不足；对普通用户学习曲线陡                 |
| **PrismLauncher**        | 全球最大开源启动器（MultiMC 继承者）；社区活跃度最高；跨平台最成熟；实例管理最强大                 | 界面功能导向，缺乏美学设计；上手门槛高，不适合新手；下载源单一（默认 Mojang），国内速度差；无内置社区功能             |
| **ATLauncher**           | 整合包生态最强（自有平台）；Modpack 制作工具成熟                                  | 偏向整合包用户，通用性不足；Electron 版本（v4）仍在开发中                                   |
| **Badlion/Lunar Client** | PvP 优化极致；内置 FPS 提升 Mod；社交功能完善                                 | 本质是客户端而非启动器；仅支持特定版本；付费墙限制大量功能                                        |

### 0.2 Bonjour 的破局点

```
竞品做不到，但 Electron + React + 现代设计系统能做到的：

1. 影院级视觉体验 → PCL2/HMCL 受限于 WPF/JavaFX 做不出
2. 毫秒级启动器响应 → Electron 比 JavaFX/.NET 冷启动更快（热启动更是碾压）
3. 真正的跨平台一致性 → HMCL/PrismLauncher  跨平台但 UI 体验各平台割裂
4. Web 技术栈的生态红利 → npm 生态、AI 集成、实时协作、数据可视化远强于 Java/.NET
5. 设计师可直接参与 → CSS/Tailwind 比 JavaFX FXML/XAML 的设计效率高 10x
```

### 0.3 不做的事（反目标）

- ❌ 不做模组 IDE —— 那是 IntelliJ/VSCode 的事
- ❌ 不做游戏主机/云游戏 —— 3 年内无可行性
- ❌ 不做区块链/NFT —— 社区反感，品牌自杀
- ❌ 不做社交平台 —— Discord 已垄断，应与之集成而非竞争

## 一、首次体验与安装向导（8个方向）

> **为什么是这个模块？** 竞品分析发现：PCL2/HMCL/PrismLauncher 的首次安装体验要么不存在，要么极其简陋。用户在没有任何引导的情况下面对空白界面。这是最大的流失节点。

**#1 零配置启动向导**

- **竞品痛点**：PCL2 打开后需要手动设置 Java 路径、游戏目录；HMCL 空白界面让新手无从下手
- **具体方案**：三步向导（检测硬件→推荐版本→一键安装），全程自动完成 Java 下载、目录设置、首个版本安装
- **技术路径**：硬件检测（CPU/GPU/RAM）→ 匹配版本兼容矩阵 → Adoptium API 自动下载对应 Java → BMCLAPI 下载推荐版本
- **可量化目标**：从下载启动器到进入游戏 < 5 分钟（PCL2 首次体验平均 15-20 分钟）

**#2 迁移助手：从竞品无缝切换**

- **竞品痛点**：切换启动器的最大阻力不是功能对比，而是迁移成本（已有存档、模组、配置都在旧启动器里）
- **具体方案**：自动检测系统中的 PCL2/HMCL/PrismLauncher/官方启动器，一键导入所有实例、存档、模组、配置
- **技术路径**：解析各启动器的配置格式（PCL2 的 JSON 配置、HMCL 的 hmcl.json、MultiMC 的 instance.cfg）→ 自动映射到 Bonjour 实例结构
- **可量化目标**：迁移成功率 > 95%；迁移后首次启动成功率 > 90%

**#3 智能 Java 运行时管理**

- **竞品痛点**：所有竞品都需要用户手动下载/配置 Java，PCL2 虽有自动下载但只提供有限的版本选择
- **具体方案**：启动器内嵌 Java 版本管理器，自动为每个游戏版本匹配最优 Java 版本（1.16.5 需要 Java 8，1.20+ 需要 Java 21），多版本 Java 并行共存
- **技术路径**：Adoptium API 自动拉取 → 按需下载到 `{dataDir}/java/versions/{major}/` → 游戏启动时自动选择对应版本
- **可量化目标**：Java 相关问题导致的启动失败率从行业平均 25% 降至 < 5%

**#4 预检系统：启动前自动诊断**

- **竞品痛点**：PCL2/HMCL 都是等用户点击启动后才报错，用户反复尝试浪费时间
- **具体方案**：在选择版本后立即运行预检（Java 存在？版本兼容？内存足够？磁盘空间？显卡驱动？），给出明确的一键修复按钮
- **技术路径**：预检规则引擎（可扩展 YAML 规则库）→ 检查 30+ 项 → 分级结果（通过/警告/阻断）
- **可量化目标**：预检覆盖 95% 常见启动失败原因；阻断级问题在点击启动前 100% 检出

**#5 后台静默更新**

- **竞品痛点**：PCL2 更新需要手动下载安装包；HMCL 更新需要重启；PrismLauncher 无自动更新
- **具体方案**：启动器自身静默增量更新，用户无感知自动升级
- **技术路径**：electron-updater → 增量更新（bsdiff）→ 下次启动器冷启时自动替换 → 仅在托盘通知「已更新」
- **可量化目标**：更新包大小 < 5MB（全量 80MB+）；更新成功率 > 99%

**#6 视觉效果首次展示（不可跳过的 WOW Moment）**

- **竞品痛点**：竞品启动器打开的第一屏毫无设计感 — PCL2 是白色网格、HMCL 是空白侧边栏
- **具体方案**：首次启动展示 3 秒品牌开场动画（Minecraft 像素风 Logo 粒子汇聚），然后无缝过渡到色彩浓郁的版本画廊页面
- **技术路径**：WebGL/Canvas 像素粒子动画 → framer-motion 无缝过渡 → 保留为可选的后续启动动画
- **可量化目标**：首次用户 7 日留存率相比无动画组提升 15%+（A/B 测试验证）

**#7 区域自感知配置**

- **竞品痛点**：国际用户用 Mojang 源下载慢，中国用户用 BMCLAPI 但需要手动配置
- **具体方案**：启动时基于地理位置自动选择最优下载源（中国→BMCLAPI，亚太→Modrinth CDN，欧美→Mojang 官方），多源自动故障转移
- **技术路径**：IP 定位（无需精确，仅判断区域）→ 延迟测速（对每个候选源做 HEAD 请求）→ 自动排序
- **可量化目标**：全球 95% 用户首次下载速度 > 5MB/s

**#8 离线模式降级策略**

- **竞品痛点**：HMCL/PrismLauncher 断网时大量功能不可用，甚至无法查看已安装版本
- **具体方案**：智能检测网络状态，无网络时自动降级为离线模式：仅展示已缓存内容、禁用在线搜索、本地资料库仍可搜索
- **技术路径**：navigator.onLine + 心跳检测 → 渐进式功能降级 → 网络恢复后无缝恢复
- **可量化目标**：离线模式下核心功能可用率 100%（启动已安装版本、管理实例、查看配置）

## 二、核心启动引擎（10个方向）

> **为什么是这个模块？** 这是启动器存在的根本理由。核心洞察：启动失败是用户流失的首要原因。当启动失败时，70% 的新手会放弃并卸载。

**#9 启动流程可视化仪表盘**

- **竞品痛点**：PCL2 的启动日志是单色文本框；HMCL 日志混在控制台输出中；PrismLauncher 日志需要切换标签页查看
- **具体方案**：实时可视化展示 7 个启动阶段（验证→Java 初始化→下载→解压→类加载→资源加载→窗口创建），每个阶段显示耗时和并行任务数
- **技术路径**：minecraft-launcher-core 事件流 → 阶段状态机 → Canvas 绘制时间线 → 鼠标悬停显示每条日志
- **可量化目标**：用户定位启动瓶颈的平均时间从 5 分钟降至 30 秒

**#10 启动日志智能诊断引擎**

- **竞品痛点**：所有竞品的日志只是「展示」，需要用户自己读懂。Exit Code 1 对 99% 的用户毫无意义
- **具体方案**：日志流经规则引擎，实时匹配已知错误模式，用中文白话解释「发生了什么」+ 「怎么办」
- **技术路径**：正则 + 关键词匹配（第一阶段）→ 嵌入向量语义匹配（第二阶段）→ 社区贡献的规则库 → 匹配成功后显示「Exit Code 1 = 显卡驱动版本过旧，请更新驱动」而非原始日志
- **可量化目标**：85% 的启动失败能被自动诊断并提供可行修复方案

**#11 JVM 参数调优向导**

- **竞品痛点**：PCL2 有参数编辑框但无建议；HMCL 有预设但解释不足
- **具体方案**：分三个层级 —「小白模式（自动最优）」、「进阶模式（可视化滑块）」、「专家模式（自由编辑）」，每个参数配有中文解释和推荐值
- **技术路径**：参数知识库（GC 选择、内存比例、JIT 阈值等）→ 自适应推荐 → 滑块控件直接映射参数值
- **可量化目标**：使用自动推荐参数的启动性能不低于手动调优专家的 90%

**#12 崩溃报告自动收集与分析**

- **竞品痛点**：PCL2/HMCL 的崩溃报告只存在本地 .txt，用户需要在论坛手动上传
- **具体方案**：崩溃时一键生成结构化报告（系统信息、模组列表、崩溃堆栈、启动参数），可选匿名上传到社区知识库，AI 匹配已知解决方案
- **技术路径**：崩溃堆栈解析 → 结构化 JSON → 脱敏上传 → 向量搜索匹配相似案例
- **可量化目标**：社区知识库覆盖 1000+ 常见崩溃模式；匹配准确率 > 80%

**#13 增量资源补全**

- **竞品痛点**：PCL2 安装版本时「下载 libraries」阶段最容易中断，重试又从头开始
- **具体方案**：每次下载前检查本地已有文件（Hash 校验），仅下载缺失或损坏的文件，支持断点续传
- **技术路径**：版本 JSON 解析 → 本地文件清单对比 → 缺失列表 → 并发下载（8 线程）→ SHA-1 校验
- **可量化目标**：版本重装/修复的时间减少 80%（跳过已存在的文件）

**#14 启动耗时基准测试**

- **竞品痛点**：无从对比「我的启动算快还是慢」；换了 Java/加了模组后的性能变化不可感知
- **具体方案**：每次启动自动记录耗时，建立个人历史基线，标注偏离（「本次比平均慢 12 秒，新增模组 X 可能是原因」）
- **技术路径**：启动阶段计时 → 本地时序数据库（SQLite）→ 可视化趋势图 → 异常检测
- **可量化目标**：用户能在 10 秒内定位到导致启动变慢的模组

**#15 多版本并行启动（真·多开）**

- **竞品痛点**：PCL2 不支持多实例同时运行；HMCL 理论上可以但容易冲突
- **具体方案**：每个实例分配独立数据目录（`.minecraft/instances/{name}/`），完全隔离的进程空间，各自独立 Java 进程，共享只读的 libraries/assets
- **技术路径**：实例目录隔离 + 硬链接共享公用资源 + 跨进程通信监控状态
- **可量化目标**：同时运行 3 个实例时额外内存开销 < 500MB

**#16 快速启动面板（Quick Launch）**

- **竞品痛点**：每次启动都要打开启动器→选择版本→点击启动，流程太长
- **具体方案**：系统托盘右键菜单直接启动最近版本；支持设置「默认版本」，双击托盘图标即启动；Win/macOS 原生通知历史版本可一键重开
- **技术路径**：Tray API → 右键菜单注入 → 启动参数本地缓存
- **可量化目标**：从想玩游戏到点击启动减少到 1 次操作

**#17 游戏进程守护**

- **竞品痛点**：游戏崩溃后启动器完全不知道，玩家发现时已经浪费了时间
- **具体方案**：启动器监控游戏进程状态，游戏异常退出时弹出恢复选项（重启游戏/查看日志/回退版本/一键修复）
- **技术路径**：child\_process 句柄监控 → exit code 分析 → 分级响应
- **可量化目标**：游戏崩溃后的平均恢复时间从 5 分钟降至 1 分钟

**#18 热配置注入**

- **竞品痛点**：改了 JVM 参数或模组配置需要重启游戏才能生效（有些修改其实不需要重启）
- **具体方案**：标记哪些配置需要重启，哪些可热加载（如资源包切换、部分模组配置），热加载配置实时推送到游戏进程
- **技术路径**：文件监控 → 配置分类 → 热加载通道（需要配套轻量 Mod）
- **可量化目标**：50% 的配置调整无需重启游戏

## 三、实例与版本生态系统（12个方向）

**#19 实例分组与标签**

- **竞品痛点**：PCL2 的版本列表是扁平列表，堆了 30+ 个版本后难以管理
- **具体方案**：支持文件夹式层级分组（「生存档」「小游戏」「测试用」），标签系统（「高配」「光影」「联机」），自由排序
- **技术路径**：树状数据结构 → 拖拽排序 → 标签自由创建
- **可量化目标**：管理 20+ 实例时的定位时间减少 70%

**#20 实例模板系统**

- **竞品痛点**：创建新实例需要重复配置 JVM 参数、模组、资源包
- **具体方案**：保存任意实例为模板，新建实例时从模板克隆（继承配置但独立数据），模板可导入导出分享
- **技术路径**：实例序列化（不含个人数据）→ 模板仓库 → 克隆时增量创建
- **可量化目标**：创建新实例的配置时间从 10 分钟降至 30 秒

**#21 版本兼容性评分卡**

- **竞品痛点**：CurseForge/Modrinth 显示的兼容信息不直观
- **具体方案**：为每个 MC 版本维护兼容性评分卡（Dim — 模组覆盖率 / Server — 主流服务器适配 / Stable — Bug 密度 / Ready — 开箱即用度），一目了然
- **技术路径**：爬虫定期采集模组平台数据 → 统计模型 → 可视化评分
- **可量化目标**：用户选择版本时的决策时间从 3 分钟降至 30 秒

**#22 版本间差异对比**

- **竞品痛点**：没人告诉你 1.20.1 和 1.20.4 到底改了什么（对普通玩家而言）
- **具体方案**：选择两个版本时自动展示差异摘要（新方块、新生物、机制变化、地形修改），通用话语而非 patch note
- **技术路径**：Minecraft Wiki 数据解析 → 结构化差异 → 图文卡片展示
- **可量化目标**：版本对比信息密度达到「5 秒看懂差异」

**#23 时间机器：实例状态快照**

- **竞品痛点**：加了新模组导致崩溃，想回到之前的状态但没有备份
- **具体方案**：对实例的完整状态（模组列表+版本、配置、资源包）创建快照，支持一键回滚到任意历史状态
- **技术路径**：Copy-on-Write 快照（仅存储差异+元数据）→ 时间线界面 → 回滚操作为原子事务
- **可量化目标**：实例回滚操作 < 10 秒完成；单快照占用 < 50MB

**#24 实例导入/导出（可移植实例包）**

- **竞品痛点**：PCL2 的版本导出依赖第三方工具；HMCL 的导出格式不通用
- **具体方案**：一键导出实例为 `.bonjour-pkg`（包含版本信息、模组列表、配置文件索引），好友可直接导入使用
- **技术路径**：自定义打包格式（JSON 元数据 + mods 列表 URL + 配置文件）→ 导入时自动下载与校验
- **可量化目标**：导出/导入流程总耗时 < 3 分钟（含下载）

**#25 实例存储分析**

- **竞品痛点**：不知道 `.minecraft` 里几百 GB 是谁占的
- **具体方案**：可视化磁盘占用分析 — 每个实例的 breakdown（versions / libraries / assets / mods / saves / logs），标注可安全清理的冗余
- **技术路径**：递归计算目录大小 → 饼图/树状图可视化 → 安全清理规则
- **可量化目标**：用户平均可安全释放 20-30% 的磁盘占用

**#26 实例数据看板**

- **竞品痛点**：玩了几个月的存档，不知道总共花了多少时间、去了哪些维度、死了多少次
- **具体方案**：聚合分析实例的统计信息 — 总游戏时长、游玩的存档列表、服务器访问记录、模组变更历史
- **技术路径**：stats 文件夹解析 → achievements 进度 → 时间线可视化
- **可量化目标**：数据看板日活使用率 > 30%

**#27 过期版本智能降级指引**

- **竞品痛点**：某版本太老没有模组支持了，但用户不知道能迁移到哪个相近版本
- **具体方案**：检测长期未游玩且模组生态已枯竭的版本，提示「该版本模组覆盖率仅 15%，建议迁移到 X 版本（覆盖率 90%）」
- **技术路径**：版本生态数据定期更新 → 阈值触发 → 引导性通知

**#28 版本注解（社区评论）**

- **竞品痛点**：不知道某个版本的社区评价如何
- **具体方案**：为每个版本提供社区讨论区 — 玩家分享稳定性评价、已知 Bug、适配模组推荐
- **技术路径**：轻量评论系统 → 有价值的评价上浮 → 官方标注（「社区推荐」「已知问题」）
- **可量化目标**：Top 20 版本的社区标注覆盖率 100%

**#29 数据目录健康检查**

## 四、模组管理革命（12个方向）

> **为什么叫「革命」？** 当前所有启动器的模组管理本质上是文件管理器 + 搜索客户端。真正的模组管理应该是：告诉我想要什么体验，帮我构建整个模组环境。

**#31 全局模组搜索引擎**

- **竞品痛点**：PCL2 整合了 CurseForge + Modrinth 但速度一般；HMCL 搜索需要切换标签页
- **具体方案**：横跨 CurseForge / Modrinth / GitHub Releases / MCBBS / Modrinth 中文镜像，并行查询实时聚合，统一结果呈现
- **技术路径**：Web Worker 并行请求 → 结果去重与合并 → 中文名称索引增强
- **可量化目标**：搜索结果返回 < 2 秒；中文搜索相关性 > 对标 PCL2

**#32 模组批量安装队列**

- **竞品痛点**：想装 20 个模组需要逐个搜索、下载、确认，耗时 30+ 分钟
- **具体方案**：从整合包页面、推荐列表或社区分享中一键添加多个模组到安装队列，后台自动解析依赖、检查冲突、批量下载
- **技术路径**：任务队列系统 → 依赖图并发解析 → 安装前冲突预检
- **可量化目标**：批量安装 20 个模组 < 5 分钟（对比手动逐个安装 30+ 分钟）

**#33 版本组合推荐（Modpack-less 体验）**

- **竞品痛点**：整合包太重太慢，但自己搭配模组又不知道哪些是「标配」
- **具体方案**：根据想体验的内容（科技/魔法/冒险/建筑/休闲）自动生成推荐模组清单，无需下载完整整合包即可获得类似体验
- **技术路径**：内容分类矩阵 → 模组关联度模型（「装了 AE2 的人 90% 也装了的模组」）→ 轻量合集
- **可量化目标**：推荐的模组组合评分 > 4.2/5（用户反馈）

**#34 实时冲突检测沙箱**

- **竞品痛点**：现有冲突检测基于元数据匹配，但真正的冲突发生在运行时（类加载冲突、事件总线冲突、MixIn 冲突）
- **具体方案**：选好模组后，在虚拟环境中模拟启动，检测类加载冲突、ID 冲突、事件监听冲突，提前预警
- **技术路径**：轻量 Java Agent → 类加载器监控 → 冲突模式识别
- **可量化目标**：检测出的运行时冲突占实际冲突的 > 70%

**#35 模组更新策略控制**

- **竞品痛点**：更新模组要么全手动，要么全自动（可能引入不兼容更新）
- **具体方案**：支持三级更新策略 —「仅安全更新（Bug 修复）」「同大版本更新」「最新版」，每个模组独立策略
- **技术路径**：语义版本分析 → 更新安全评级 → 策略引擎
- **可量化目标**：自动更新引入的兼容性问题 < 2%

**#36 模组社区评价聚合**

- **竞品痛点**：CurseForge + Modrinth 各有各的评分，缺乏中文评价
- **具体方案**：聚合多平台评分，叠加 Bonjour 社区的中文评价和标签（「稳定」「吃配置」「必装」）
- **技术路径**：评分聚合算法（加权平均+时间衰减）→ 中文评价独立维护
- **可量化目标**：Top 1000 模组的中文评价覆盖率 > 60%

**#37 性能影响评级**

- **竞品痛点**：不知道装某个模组会让 FPS 降多少、启动慢多少
- **具体方案**：基于社区测试数据为每个模组标注性能影响等级（🟢几乎无影响 / 🟡略有影响 / 🟠明显影响 / 🔴严重影响），并给出具体数值
- **技术路径**：众包性能测试 → 统计修正 → 装机配置自动适配
- **可量化目标**：Top 500 模组的性能评级覆盖率 100%

**#38 配置迁移工具**

- **竞品痛点**：更新模组大版本后，旧的配置文件格式变了，手动迁移痛苦
- **具体方案**：检测模组更新前后的配置变更，自动迁移仍在支持的旧配置项，标记已废弃的配置项
- **技术路径**：配置 schema diff → 自动翻译 → 人工确认界面
- **可量化目标**：常见模组（Top 100）的配置迁移自动化率 > 80%

**#39 模组文件分析器**

- **竞品痛点**：从不明来源下载的模组 jar，不知道包含了什么
- **具体方案**：上传/选择 jar 后自动分析 — 模组名称、版本、加载器、依赖、混淆映射、入口类、包含的 MixIn 列表
- **技术路径**：jar 内元数据解析（mods.toml / fabric.mod.json / mcmod.info）→ 字节码扫描 → 安全风险评估
- **可量化目标**：元数据解析成功率 > 95%

**#40 模组分享链接**

- **竞品痛点**：给好友推荐模组需要发 CurseForge 链接或者传 jar 文件
- **具体方案**：生成「模组分享卡片」— 包含图标、名称、版本、一句话描述，可通过链接或二维码分享
- **技术路径**：服务端渲染卡片 → 短链接 → 扫码直接跳转启动器安装
- **可量化目标**：分享卡片点击安装转化率 > 30%

**#41 多模组加载器实例共存**

- **竞品痛点**：HMCL 创建新版本时如果已有相同 MC 版本的不同加载器实例，管理混乱
- **具体方案**：同一 MC 版本下无缝管理 Forge/Fabric/Quilt/NeoForge 多种加载器实例，实例名自动包含加载器后缀，列表中清楚区分
- **技术路径**：实例命名策略 → 加载器图标标识 → 切换对比界面
- **可量化目标**：多加载器实例管理混淆率降至 0

**#42 模组元数据云端增强**

- **竞品痛点**：扫描本地 jar 得到的模组信息很有限（通常只有文件名）
- **具体方案**：本地模组指纹（SHA-256）云端匹配，返回完整的元数据（名称、版本、描述、作者、兼容性、图标）
- **技术路径**：指纹数据库（定期同步 CurseForge/Modrinth 文件指纹）→ 本地优先+云端增强
- **可量化目标**：「unknown」模组从占比 60% 降至 < 10%

## 五、整合包系统（8个方向）

**#43 跨平台整合包一键安装**

- **竞品痛点**：PCL2 支持 CurseForge/Modrinth 安装但依赖内置解析器；HMCL 需要额外配置
- **具体方案**：支持 CurseForge / Modrinth / FTB / Technic / 自建格式，拖入 zip 文件或粘贴链接即可自动识别并安装
- **技术路径**：多格式解析器 → manifest 解析 → 依赖解析 → 并发下载 → 配置注入
- **可量化目标**：支持 5+ 主流整合包格式，安装成功率 > 95%

**#44 整合包创建工坊**

- **竞品痛点**：创建整合包需要手动打包 mod 文件夹 + 写 manifest，CurseForge 创建流程繁琐
- **具体方案**：可视化整合包编辑器 — 拖拽模组到包内，自动解析依赖关系，一键导出为标准格式或多平台发布
- **技术路径**：可视化画布 → 依赖图 → 自动 manifest 生成 → 多平台发布适配器
- **可量化目标**：创建整合包耗时从 2 小时降至 15 分钟

**#45 整合包增量更新**

- **竞品痛点**：整合包更新需要重新下载整个包（可能 200MB+），而实际只改了几个模组
- **具体方案**：记录用户已安装的整合包版本，检查更新时只下载差异部分（新增/更新/删除的模组）
- **技术路径**：版本 diff 引擎 → 增量下载 → 原子更新（失败自动回滚）
- **可量化目标**：整合包更新流量节省 70%+

**#46 整合包分身（Pack Fork）**

- **竞品痛点**：想基于某个整合包添加/删除一些模组变成自己的版本，但会丢失原包的更新支持
- **具体方案**：Fork 现有整合包为个人分支 — 保留原包更新能力的同时，叠加个人模组增删，冲突时有智能合并策略
- **技术路径**：git-like 分支模型 → 三路合并 → 冲突可视化解决
- **可量化目标**：整合包个人化定制时间从重新配置的 2 小时降至 5 分钟

**#47 整合包评分与发现**

- **竞品痛点**：整合包太多了，不知道哪些质量高、适合自己
- **具体方案**：多维评分系统（完成度/稳定性/性能/难度/创新），协同过滤推荐「玩了 X 包的人也玩了 Y 包」
- **技术路径**：多维度评分模型 → 协同过滤矩阵 → 个性化推荐
- **可量化目标**：用户找到满意整合包的平均搜索次数从 5 次降至 2 次

**#48 整合包测试实验室**

- **竞品痛点**：不确定整合包能否正常运行就安装了，装完发现启动不了浪费时间
- **具体方案**：在沙箱环境中测试整合包兼容性 — 虚拟启动检测、模组冲突预检、资源完整性校验
- **技术路径**：轻量测试环境 → 自动化测试脚本 → 兼容性报告
- **可量化目标**：安装前预检拦截 90% 的兼容性问题

**#49 整合包多人同步**

- **竞品痛点**：几个人想一起玩同一个整合包，需要各自手动安装确保版本一致
- **具体方案**：创建「整合包房间」— 发起人选择整合包版本，参与者扫描房间码自动安装完全一致的版本
- **技术路径**：PeerJS / WebRTC 信令 → 版本指纹验证 → P2P 文件传输加速
- **可量化目标**：多人环境同步 4 人 < 10 分钟

**#50 整合包性能基准**

- **竞品痛点**：整合包作者声称「轻量」，实际装了 200 个模组卡成幻灯片
- **具体方案**：为整合包建立性能基准数据库 — 最小配置要求、推荐配置、实测 FPS 范围、启动时间
- **技术路径**：社区跑分上传 → 数据清洗 → 可视化性能卡片
- **可量化目标**：Top 200 整合包的性能基准覆盖率 > 80%

**#53 存档世界地图生成**

- **具体方案**：读取存档区块数据，离线渲染全貌鸟瞰图（支持不同维度、不同缩放级别），标注玩家位置、建筑点、传送点

**#54 存档统计面板**

- **竞品痛点**：不知道自己在这个存档里创造了什么

- **技术路径**：stats 目录解析 + 区块数据补充 → 可视化仪表盘

**#55 存档格式转换与迁移**

**#59 存档日记**

**#60 存档蓝图分享**

## 七、服务器管理与多人联机（10个方向）

**#61 本地服务器一键创建**

- **竞品痛点**：PCL2 内置服务器下载但配置复杂；HMCL 无内置服务器管理
- **具体方案**：选择版本 → 自动下载服务端核心 → 可视化配置（难度、游戏模式、种子、端口）→ 一键启动 → 本机客户端自动连接

**#62 LAN 世界发现与直连**

**#63 好友联机（虚拟局域网）**

**#64 服务器收藏与管理**

- **竞品痛点**：PCL2/HMCL 的服务器列表只是地址+名字
- **具体方案**：每个服务器卡片显示实时信息（在线玩家数、当前版本、ping 延迟、MOTD 预览），支持分组管理
- **技术路径**：Server List Ping 协议 → 定时刷新 → 卡片 UI
- **可量化目标**：管理 20+ 服务器时定位时间 < 5 秒

**#65 服务器性能监控**

- **竞品痛点**：自己的服务器突然卡了，不知道原因
- **具体方案**：通过 RCOn 或 Plugin 获取服务器性能数据（TPS、内存、玩家数、实体数），可视化展示，异常时推送通知
- **技术路径**：RCON 协议 / 自定义 Plugin 数据通道 → 时序数据 → 可视化仪表盘
- **可量化目标**：支持主流服务端（Vanilla/Spigot/Paper/Fabric），数据刷新 < 2 秒

**#66 服务器资源包自动同步**

- **竞品痛点**：加入服务器弹出「是否下载资源包」，很多人点否导致体验异常
- **具体方案**：启动器接管服务器资源包下载流程，后台静默下载，游戏启动时自动加载，下载进度可见
- **技术路径**：Server List Ping 获取资源包 URL/SHA-1 → 后台下载 → 校验 → 注入
- **可量化目标**：资源包自动加载成功率 > 98%

**#67 一键模组同步到服务器**

- **竞品痛点**：自己配了一套好用的模组环境，想和朋友一起玩但需要各自手动装
- **具体方案**：将本地实例的模组集合一键复制/同步到自建的服务器目录，自动过滤仅客户端模组
- **技术路径**：模组分拣（client-only / server-only / both）→ 文件同步 → 服务端重启提示
- **可量化目标**：同步准确率 > 95%，误删服务端关键模组率 0

**#68 跨服传送门**

- **竞品痛点**：玩小游戏服需要退出→切换服务器→重新加入，流程冗长
- **具体方案**：在游戏内通过 GUI 快速切换到收藏夹中的其他服务器（需配套 Mod 或 BungeeCord 支持）
- **技术路径**：Mod 层实现 → IP+Port 快速切换 → 无需退出主菜单
- **可量化目标**：服务器切换时间从 30 秒降至 5 秒

**#69 服务器社区推荐**

- **竞品痛点**：找服务器要么去贴吧/论坛，要么盲搜，质量参差不齐
- **具体方案**：建立服务器发现市场，社区评分+标签筛选（「生存」「RPG」「小游戏」「养老」），支持中文服务器优先展示
- **技术路径**：服务器注册 + 信息上报 + 评分系统 + 分类筛选
- **可量化目标**：收录中文服务器 1000+，评分活跃服务器 > 200

**#70 服务器实时状态推送**

- **竞品痛点**：服务器维护/重启/更新时玩家不知道，反复连接浪费时间
- **具体方案**：收藏的服务器状态变更时（在线→离线、版本更新、活动开始），通过系统通知推送给用户
- **技术路径**：定时健康检查 → 状态变更检测 → 系统级通知
- **可量化目标**：通知延迟 < 1 分钟

## 十二、安全与隐私（5个方向）

**#104 模组安全扫描**

- **竞品痛点**：PCL2/HMCL 无模组安全检测；恶意模组屡见不鲜

- **技术路径**：字节码分析 → 行为模式匹配 → 风险等级（安全/可疑/危险）
- **可量化目标**：已知恶意模组检出率 > 95%

**#105 隐私仪表盘**

- **竞品痛点**：不知道启动器收集了什么数据
- **具体方案**：透明展示所有数据使用情况 — 什么数据、为什么需要、存储在哪里、是否上传，所有遥测均需用户同意
- **技术路径**：隐私声明系统 → 每项数据开关 → GDPR 合规

**#106 家长控制**

- **竞品痛点**：孩子沉迷 Minecraft 无有效管控
- **具体方案**：家长面板 — 设置每日游戏时长上限、限制可访问的服务器、禁止多人聊天、游戏报告
- **技术路径**：使用时间追踪 → 限制策略引擎 → 密码保护设置

**#107 文件完整性校验**

- **竞品痛点**：下载的文件损坏或被篡改难以发现

**#108 数据备份保险箱**

- **竞品痛点**：配置/存档丢失无后悔药
- **具体方案**：关键数据（配置、账号信息、实例定义）自动加密备份到用户指定位置（本地/云端/外部硬盘）
- **技术路径**：增量备份 → AES-256 加密 → 多目的地 → 定期校验

- Minecraft Realms $7.99/月 → Bonjour Pro 同价位，提供不同价值维度

## 📝 总结

本规划书围绕一个核心命题展开：**在 2026 年，为什么一个 Minecraft 玩家应该选择 Bonjour？**

答案是四个不可替代的维度：

1. **视觉与体验** — Electron + React + 专业设计系统，做出竞品 WPF/JavaFX 永远做不到的影院级体验

3. **零门槛体验** — 从竞品迁移到首次启动到崩溃修复，每个环节都比竞品少 80% 的操作
4. **开放生态** — 插件系统 + CLI + Web API，吸引开发者共建生态
